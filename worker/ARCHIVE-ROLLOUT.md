# Обновление тестового Worker: архив и восстановление

Эта ветка основана на PR #4 (`7fecd41`). PR #4 не объединён автоматически. Сайт, рабочий Worker, webhook и удалённые базы не менялись. Локальные тесты используют только синтетические записи.

## Подготовленные файлы

- `wedding-rsvp-api.js` — тестовая сборка. Временные `/delete` и `/clear_test` работают только при `ENABLE_TEST_DELETIONS=true`; при проверке этого обновления оставьте `false`.
- `wedding-rsvp-api.production.js` — финальная сборка: временные обработчики `/delete`, `/clear_test` физически отсутствуют. Доступно только отдельное подтверждаемое `/erase ID`, без массового удаления.
- `migrations/0002_archive_lifecycle.sql` — новая миграция поверх 0001; добавляет `archived_at`, таблицу подтверждений и обновляет защитные триггеры. Не пересоздаёт базу, не переписывает и не удаляет ответы.

## Безопасная последовательность (выполняется владельцем отдельно)

1. Убедиться, что открыт **тестовый** `wedding-rsvp-api-test`, а binding `DB` указывает на **тестовую** `wedding-rsvp-db-test`. Названия здесь — ожидаемые имена из шаблона; проверить фактические ресурсы и ID. Не использовать `wedding-rsvp-api` / `wedding-rsvp-db`.
2. Сохранить текущий исходник тестового Worker, переменные и экспорт тестовой D1. Сделать это до миграции. Не менять основной Telegram webhook. Для тестов нужен отдельный тестовый бот и его существующий webhook.
3. В копии `worker/wrangler.example.jsonc` (например, `worker/wrangler.local.jsonc`) заполнить **только ID тестовой D1**, оставить тестовые имена, `ENABLE_TEST_DELETIONS=false`. Не коммитить локальные настройки и секреты.
4. Проверить схему и журнал миграций в тестовой D1: `PRAGMA table_info(rsvp_responses);` и `SELECT name FROM d1_migrations;`. 0001 должна быть уже применена, `archived_at` ещё отсутствовать. Если 0001 выполнялась вручную и не записана в журнал — остановиться: не запускать её повторно; сначала согласовать фиксацию исходного состояния. Не применять 0002 повторно.
5. Из корня проекта проверить список:

   ```powershell
   npx wrangler d1 migrations list wedding-rsvp-db-test --remote --config worker/wrangler.local.jsonc
   ```

   В списке ожидается **только `0002_archive_lifecycle.sql`**. Если показана 0001 или другая миграция, остановиться.

6. В короткое окно без тестовых отправок/команд применить:

   ```powershell
   npx wrangler d1 migrations apply wedding-rsvp-db-test --remote --config worker/wrangler.local.jsonc
   ```

   Проверить сохранность количества записей/ID и наличие `archived_at`. Все существующие строки должны иметь NULL. Команды миграций и выбор базы описаны в [документации Cloudflare](https://developers.cloudflare.com/d1/reference/migrations/) и [Wrangler D1](https://developers.cloudflare.com/workers/wrangler/commands/d1/).
7. В редактор **тестового** Worker загрузить полный `worker/wedding-rsvp-api.js`. Сохранить существующие тестовые секреты, binding, cron. Убедиться, что webhook тестового бота принимает `message` и `callback_query`; основной webhook не переключать. Не включать логирование тел запросов/персональных ключей. Сайт оставить в демо-режиме.
8. На специально созданной синтетической анкете проверить `/archive ID` → подтверждение, `/archived`, исключение из `/stats`, `/guests`, `/drinks`, `/parking`, `/export`; затем `/restore ID`. Одобренная парковка после восстановления должна быть `pending`. Старые кнопки должны быть отклонены. Проверить отказ при нехватке мест из 8. **Существующие тестовые анкеты не удалять.** `/erase` проверять только после отдельного разрешения на удаление конкретной синтетической записи; локальные тесты уже покрывают этот путь.

## Поведение и ограничения

Архивирование сохраняет ID, хеш ключа, ответы и квитанции; повышает revision. Архивные анкеты исключены из активных выборок и новых уведомлений, их неподтверждённые отправки отменяются. Уже отправленное сообщение Telegram отозвать нельзя; внешний HTTP-запрос, который успел начаться перед архивированием, также может завершиться. Его старые кнопки не могут изменить анкету.

Восстановление сохраняет ID/ключ и повышает revision. Запрашиваемая парковка всегда возвращается на рассмотрение, даже если место раньше было одобрено. SQL-триггеры не допускают обхода лимита 8 и восстановление сразу в approved.

Подтверждения действуют 5 минут, связаны с администратором, личным чатом, epoch, ID и revision; повтор, чужое подтверждение или изменившаяся анкета не изменяют данные. `/erase ID` — отдельное необратимое действие с подтверждением, удаляет одну анкету и зависимые квитанции/очередь, меняет epoch против восстановления удалённого ID. У остальных гостей после смены epoch может потребоваться повторное чтение текущей анкеты.

Не откатывать Worker к версии без поддержки архива после первых архивных операций: старая версия снова включит архивные строки в отчёты. При проблеме остановить тестирование и исправить новую версию; восстановление базы из экспорта требует отдельного решения и может потерять более поздние изменения. Не запускать обратный DROP самостоятельно.

## Проверки в этой ветке

```powershell
node scripts/build-worker.mjs
node scripts/build-worker.mjs --without-test-deletes
node --test --test-concurrency=1 tests/*.test.mjs
node tests/miniflare-smoke.mjs
node tests/manual-browser.mjs
```

Проверяются реальный локальный workerd/D1, миграции, конкурирующие подтверждения парковки, архив/восстановление, ключи, повторы, условные данные, очередь, CSV, старые команды и Chromium-адаптер. CSV имеет UTF-8 BOM, `sep=;`, 14 русских колонок и защиту от формул. Байты и разбор кавычек/разделителей/переносов проверены автоматически. Открытие в настоящем Excel Windows ru-RU ещё нужно проверить вручную: `/export` на тестовом боте, кириллица, отдельные колонки, многострочный комментарий и отсутствие выполнения формул.
