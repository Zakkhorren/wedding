# RSVP v2 — подготовка и порядок подключения

## Статус этой поставки

Это подготовительный этап, **не замена работающего wedding-rsvp-api**.

- Анкета на компанию подготовлена на сайте: числовой `guestCount`, минимум 1, имена остальных только при количестве больше 1. Парковка/напитки/численность доступны только при подтверждении присутствия.
- `site.config.js → rsvpEndpoint` сохранён пустым. Опубликованная анкета остаётся демонстрационной: ответы не сохраняются и не отправляются.
- `worker/telegram-worker.js` оставлен без изменений. Это старый пример, загружать его в Cloudflare нельзя.
- `worker/rsvp-policy.mjs` и `worker/turnstile-verifier.mjs` — отдельно протестированные заготовки. Они НЕ подключены к существующему Worker, не создают таблицы/маршруты/webhook и не активируют Turnstile на сайте.
- Постоянные ID, ссылки редактирования, серверная идемпотентность, атомарное подтверждение парковки, команды Telegram и административное удаление пока НЕ подключены. Полный файл для ручной загрузки будет собран после сверки актуального исходника и схемы.

## Что нужно прислать сейчас

1. Актуальный исходник Worker `wedding-rsvp-api` из Cloudflare → Workers & Pages → Edit code. Все его файлы, если он состоит из модулей. Значения секретов удалить; оставить только обращения к `env.*`.
2. Схему `wedding-rsvp-db`, без анкет и персональных данных. В D1 Console выполнить **только чтение**:

```sql
SELECT name, type, sql FROM sqlite_master
WHERE type IN ('table', 'index', 'trigger') AND name NOT LIKE 'sqlite_%'
ORDER BY type, name;
```

3. Текущий путь webhook, список поддерживаемых команд и имена используемых переменных окружения. Значения BOT_TOKEN, ADMIN_IDS, WEBHOOK_SECRET, TURNSTILE_SECRET и другие секреты не присылать.
4. Публичный Turnstile sitekey после создания виджета (это не секрет). Если виджет уже существует — указать его режим и разрешённые hostname.

До сверки исходника не менять Worker, схему D1, webhook и endpoint сайта. Не очищать базу.

## Семантика данных, которую уже проверяют тесты

- Одна запись = одна компания = одна анкета. `guestCount` — целое число, минимум 1 при положительном ответе; при отказе/«позже» — 0. Имена не используются для подсчёта.
- `drinks` — множество вариантов компании. Каждый вариант прибавляет **одну компанию**, независимо от `guestCount`. `otherDrink` сохраняется отдельно.
- При отказе/«позже» исключаются неактуальные дополнительные гости, напитки и парковка.
- `carCount` — запрошенные машины; разрешён запрос больше 8. Подтверждённая вместимость — строго 8.
- Изменение количества машин или повторная заявка после отказа от парковки → `pending`. Изменение только сообщения, напитков или количества людей сохраняет прежнее согласование при неизменной заявке на машины.
- `/stats`: анкеты/компании — число актуальных записей; подтверждённые гости — сумма `guestCount` у положительных ответов; ожидающие ответ и отказавшиеся — **число компаний**, показывать единицу измерения явно.
- `/guests`: имя компании/представителя + численность + дополнительные имена, без извлечения количества из текста.
- CSV экспортирует только явный список публичных полей анкеты, без ключей/хешей. Строки, похожие на формулы, экранируются.

## Обязательная серверная интеграция после получения исходника

### ID, редактирование и безопасный повтор

- Клиент создаёт криптографически случайный ID и 256-битный ключ до первого запроса, сохраняет их в том же браузере. Не создавать новую пару после обычной сетевой ошибки.
- Сервер хранит только хеш ключа, привязанный к ID. Проверка нужна для чтения и обновления. Подготовлены `editKeyHash()`/`verifyEditKey()`; это ещё не авторизованные маршруты.
- Ключ передавать только в заголовке авторизации HTTPS-запроса; не в query string и не в ID. Ссылка редактирования использует фрагмент `#...`, который не отправляется серверу; после чтения удалить фрагмент из адресной строки. Не включать ключ в analytics, console, ошибки, CSV или Telegram.
- Уникальный индекс на ID и квитанции идемпотентности в D1. Повтор одного request ID с тем же телом возвращает сохранённый результат; с другим телом — конфликт. Проверка ключа обязательна и при повторе. Ревизия записи предотвращает потерю изменений с другого устройства.
- Ответ об успехе выдаётся только после успешного коммита D1. Сбой Telegram не превращает уже сохранённую анкету в «не сохранена»: сообщения через устойчивую очередь/outbox и повторную доставку без дублирования записи.
- После финальной очистки старый ID должен получать отдельный подтверждённый ответ «запись больше не существует», после чего гость может явно создать новую анкету. Таймаут/503/ошибка Turnstile не должны сбрасывать ID.

### Turnstile

- Создать виджет для `zakkhorren.github.io`; секрет хранить только в Worker Secrets. Публичный sitekey подключать к клиенту только вместе с готовым сервером.
- Подготовленный verifier проверяет Siteverify, `success`, точный hostname и action `rsvp`, ограничивает размер токена, обрабатывает таймаут/ошибки и не раскрывает секреты.
- Токен действует 5 минут и одноразовый; при истечении/повторном использовании клиент должен получить новый challenge, сохранив ID анкеты и ID запроса сохранения. `verificationId` нужен для повторной проверки Siteverify при неопределённом исходе сети.
- Браузерный виджет и проверка не активированы до серверной интеграции.

### Строгая парковка и Telegram

- Подтверждение делать одним атомарным SQL-изменением/транзакцией с проверкой актуальной ревизии и суммы подтверждённых машин. **Не** выполнять отдельные «прочитать остаток → записать подтверждение». Все способы записи должны соблюдать один инвариант вместимости.
- Нужны интеграционные тесты с реальной локальной D1: два администратора одновременно запрашивают последние места; суммарно одобрено не больше 8. Тесты JS-функции статистики этого не доказывают.
- Проверять ADMIN_IDS для каждой команды и каждого callback_query, а также секрет webhook. `answerCallbackQuery` нужен для всех исходов. Уникальный update_id предотвращает повторное действие Telegram.
- Сохранить действующие команды. Добавить `/stats`, `/guests`, `/drinks`, `/parking`, `/export`, подтверждение/отклонение/отмену парковки, сообщения с изменёнными полями.
- Webhook должен принимать `message` и `callback_query` в `allowed_updates`; путь определяется актуальным Worker. Не перенастраивать webhook до готовности обработчиков.

### Временное удаление

- Только административные Telegram-команды/callbacks, без публичных маршрутов удаления.
- Для удаления одной анкеты и всех тестовых записей нужны отдельные подтверждения: одноразовый токен, ограниченный срок, привязка к администратору/действию/записи и её ревизии. Подтверждение очистки не должно захватить записи, появившиеся после показа предупреждения.
- Удалять запись, зависимые квитанции/уведомления/парковочные данные транзакционно. Статистика строится заново по текущим строкам.
- Функции выделить в отдельный модуль и флаг; выключенный флаг должен блокировать серверный обработчик, а не только скрывать кнопки. После явного разрешения на финальную очистку — отдельный коммит с удалением обработчиков и отключением этой возможности.
- Сейчас ни удаление, ни очистка не реализованы и не запускались.

## Что сделать в Cloudflare до следующего этапа

Пока только получить исходник/схему (см. выше), проверить наличие binding `DB → wedding-rsvp-db`, создать резервную копию D1 и при необходимости создать Turnstile-виджет. Не вводить секреты в GitHub или клиентский JS. Существующие переменные/команды не переименовывать.

После сверки будут подготовлены полный обновлённый Worker, точная миграция под текущую схему и инструкция ручной загрузки. Последовательность: локальные интеграционные тесты → резервная копия → миграция → загрузка Worker → secrets/bindings → webhook с callback_query → серверные проверки → только затем отдельное подключение endpoint и sitekey на сайте.

## Проверки

```shell
node --test tests/*.test.mjs
node tests/company-browser.cjs
```

Браузерная проверка использует локальный Playwright (`npm install --no-save --package-lock=false playwright`, затем `npx playwright install chromium`), тестовый HTTP-сервер и перехваченный POST. Реальные анкеты в API/Telegram не отправляются. Скриншоты сохраняются в локальную `.qa/`.
