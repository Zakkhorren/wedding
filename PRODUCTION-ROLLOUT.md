## Состав пакета

- `worker/wedding-rsvp-api.production.js` — финальный самодостаточный Worker, без `/delete` и `/clear_test`. Архив/восстановление и отдельный подтверждаемый `/erase` сохранены. Его исходники, серверная логика и миграции в этой ветке не меняются.
- `worker/migrations/0001_rsvp_v2.sql`, затем `0002_archive_lifecycle.sql` — для подтверждённой legacy production. Данные не удаляются. Новых миграций нет. Не использовать legacy-schema fixture и TEST dump.
- `site.config.js`, `script.js`, `rsvp-ui.mjs` — production режим обычного URL, endpoint рабочего API, реальный Turnstile, редактирование/копирование/восстановление. Сохранены прежние визуальные компоненты, ID/ключи/повторы, условная парковка, guestCount, архивные ошибки.
- `rsvp-session.mjs`, `rsvp-turnstile.mjs`, `worker/rsvp-policy.mjs` — прежние адаптер/Turnstile/политика, без изменений. Последний файл нужен клиенту: не исключать его из Pages.
- `rsvpMode: 'maintenance'` — безопасная остановка на клиенте без демо-success и без очистки localStorage. Это не серверная блокировка: открытые до переключения вкладки могут продолжить отправку.
- `scripts/check-production.mjs` — только offline-проверка конфигурации и SHA256 файлов, без сетевых запросов/деплоя.
- `tests/rsvp-production-browser.mjs` — обычный production URL → финальная сборка на локальном workerd/D1 с обеими миграциями. Все сетевые запросы перехвачены или заблокированы, настоящий production не вызывается.

### Оставшийся параметр

В `site.config.js` требуется **публичный Site key** существующего виджета wedding-rsvp-form. Secret key остаётся в Cloudflare. Пока публичный ключ пуст, форма безопасно блокируется, `npm.cmd run check:production` завершается с BLOCKED. Не публиковать пакет с пустым/примерным ключом. Наличие секретов в Worker не позволяет получить из них публичный Site key.

## Локальная проверка на Windows

Из отдельной чистой папки, не поверх вручную изменённого preview:

```powershell
git fetch origin
git worktree add --track -b review/rsvp-production ..\wedding-production-review origin/feat/rsvp-production

npm.cmd test
npm.cmd run test:rsvp
npm.cmd run test:production
node tests/miniflare-smoke.mjs
npm.cmd run check:production
```

Node 24+. Если имя worktree/ветки занято, выбрать другое, ничего не удалять. Последняя команда ожидаемо блокируется, пока не указан настоящий публичный Site key. Автотесты используют только локальные токены/Telegram-моки, не считаются реальной production-отправкой. Не применять старый `--test-api` с Playwright.

Для ручного локального просмотра production-флоу: `npm.cmd run preview -- --production`. Откроется изолированное окно с локальными Worker/D1/Turnstile/Telegram, обычным URL и явной подписью о локальной проверке. На настоящие адреса запросы не уходят. Это не повтор облачного E2E.

Проверить diff production-PR относительно #8: дизайн/фотографии/шрифты/анимации/серверные сборки/SQL не должны меняться. Перед запуском зафиксировать SHA коммита, хеш финального Worker и обоих SQL из check:production. Не добавлять backup, `.env`, `.dev.vars` или локальные Cloudflare-конфиги в Git.

## Порядок запуска — только после отдельного согласования

### 3. Объединение цепочки PR и Pages

У каждого push в main срабатывает Pages. Не объединять все PR одновременно и не считать их объединение «только серверной подготовкой».

| Порядок | PR/base перед merge                                                    | Публичная форма после этого           |
| ------- | ---------------------------------------------------------------------- | ------------------------------------- |
| 1       | #4 → main                                                              | Старое демо                           |
| 2       | #5: сменить base на main после #4, проверить diff                      | Старое демо                           |
| 3       | #6: сменить base на main после #5, проверить diff                      | Старое демо                           |

| 5       | Новый production-PR: сменить base с feat/rsvp-preview на main после #8 | Реальная форма, только теперь         |

Использовать **Create a merge commit** для стека, без squash/rebase, чтобы сохранить ancestry и избежать повторного внесения нижних PR. Не удалять ветку-основу до retarget зависимого PR. GitHub может retarget автоматически — всё равно проверить base/diff, отсутствие конфликтов и посторонних файлов. Если правила репозитория не позволяют merge commit, остановиться и отдельно подготовить перепривязку/rebase стека вместо слепого squash.

После КАЖДОГО merge дождаться успешного Actions Pages и проверить, что обычный сайт ещё демо (до последнего PR). После финального Pages success открыть обычный URL в чистом Edge/Chrome с отключёнными Overrides, без preview query. Проверить все .mjs (включая worker/rsvp-policy.mjs) доступны с JS MIME, без 404. Нельзя публиковать реальный клиент раньше сервера.

Не копировать весь root checkout с локально изменённым workflow: в старом корне есть несогласованная локальная правка Pages. В этой production-ветке workflow не меняется. ### 4. Проверка после запуска

1. Сначала без записей: обычный URL, реальный Turnstile, отсутствие demo/preview надписей, desktop/mobile, Console без ошибок, правильные endpoint/CORS. Не снимать HAR/логи с Authorization и edit-key.
2. С отдельным разрешением и предупреждением организаторов — **одна настоящая анкета согласованного участника**, не Василий и не тестовое имя. Дождаться saved:true и уведомления настоящему боту, проверить 1 активную запись, guestCount и данные. Эта отправка создаёт реальные данные и сообщение, поэтому не является частью текущей подготовки.
3. Изменить эту же анкету, обновить страницу, скопировать ссылку и открыть на другом устройстве. ID прежний, revision растёт, число записей не увеличивается. Ссылка без rsvp_preview и ключ только в fragment; публичные запросы/экспорт ключ не содержат.
4. Если участник реально запросил парковку, сообщение pending; после согласованного решения администратора fresh restore показывает approved/rejected. Запрос не означает бронь. Не занимать искусственно все 8 мест ради production-smoke: конкуренция, лимит и архив покрыты локальными/TEST тестами. Изменение машин возвращает pending, сообщение/напитки не сбрасывают решение. Архив/восстановление/erase не выполнять на реальных анкетах ради запуска.
5. Согласованно проверить команды организаторов stats/guests/drinks/parking/export XLSX. Напитки считаются по компаниям, парковка — по числу approved машин ≤8. Старые callback-кнопки могут быть отклонены: использовать свежий `/parking`, а не старые решения.
6. Сразу, через 15–30 минут и на следующий день: ошибки отправки/Turnstile, outbox retries и webhook pending/errors, отсутствие дублей. Telegram delivery at-least-once: сетевой таймаут может повторить уведомление, не анкету. Не удалять записи или задания автоматически.

## Тестовые данные не переносятся

- Не импортировать в production TEST/временную D1, TEST outbox, ID, receipts, epoch или browser storage. Переносятся только код и schema migrations.
- Разные D1 UUID и production bot token сверены отдельно. TEST бот/webhook не изменяется.
- localStorage разделён полным API endpoint. Production игнорирует TEST storage, а ссылки с rsvp_preview отклоняются до открытия session/API; их hash очищается как и раньше. Не редактировать вручную TEST-ссылку, удаляя её метку: это всё равно не переносит сохранённую анкету. Гости используют только production-ссылки.
- Не создавать Василия Пупкина в production. Production пуста, миграции ничего не засевают, тесты этой ветки не имеют доступа к remote Worker/Telegram. Проверенные временные базы оставить отдельно, не чистить их без разрешения.

## Безопасный откат

1. Если ошибка только клиента: отдельный срочный commit `rsvpMode: 'maintenance'` в production site.config.js и Pages deploy. Показан честный отказ отправки, localStorage/pending/ключи не очищаются. По возможности подготовить этот commit/PR заранее после финального release SHA. Он не останавливает уже открытые вкладки — при серьёзной серверной проблеме нужна отдельно согласованная серверная остановка записи.
2. Исправление вперёд предпочтительнее. Не возвращать старый demo-success под видом настоящего сохранения. Не переключать пользователей на TEST endpoint, не чистить хранилище браузера и не создавать новый ID при неизвестном исходе.
3. Worker откатывать только к совместимой с v2+архивом версии. Старый legacy Worker не поддерживает новые ключи/архив и после первых ответов небезопасен для отката. При первом запуске предыдущей совместимой production-версии ещё может не быть: тогда maintenance/остановка writes + исправление, а не слепой rollback. До новых ответов возврат legacy возможен только с сайтом в демо/maintenance и отдельным решением.
4. Миграции не откатывать DROP/ALTER вручную. Схему с добавленными столбцами можно оставить при frontend-проблеме. Restore backup/Time Travel — только при повреждении данных и отдельном разрешении: остановить всех writers/cron, сохранить текущую БД, учесть все новые ответы после backup. Уже проверенная копия пуста: её восстановление после запуска УДАЛИТ новые реальные ответы! Восстановление старого outbox может повторить уведомления. Нельзя восстанавливать пустой backup как обычный откат сайта.
5. После исправления сверить ID/revision/epoch/очередь и занятые места, затем отдельно разрешить возобновление. Не удалять анкеты и не менять webhook бота для отката frontend.
